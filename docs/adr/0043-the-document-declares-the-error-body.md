# ADR-0043: The published document declares the error body the API actually sends

**Status:** Accepted · **Date:** 2026-08-18 · Corrects the generation pipeline described in
[ADR-0029](0029-contract-conformance-gate.md) (the contract conformance gate) and
[ADR-0023](0023-runtime-response-validation.md) (runtime response validation), which both consume
`docs/api/openapiv1.json`. Supersedes neither.

## Context

`openapiv1.json` is generated from the API, committed, and everything downstream is generated from
it: the frontend's `schema.d.ts` and its runtime Zod validators. So a claim in that file is not
documentation, it is a type a client compiles against.

Measured on `main` @ `6c3b24e`, one HTTP call per row against the running API:

| what the document said | what the API answers |
| --- | --- |
| 23 × `401`, no body | `application/json`, 243 bytes, seven keys |
| 23 × `403`, no body | `application/json`, 260 bytes, seven keys |
| 7 × `404`, no body | seven keys, `errorCode` naming the resource |
| 4 × `400` on `{id:guid}` routes | the route never matches — the framework answers **404** |
| 1 × `404` on `/api/users/{azureTag}` | **200**, `{"exists": false}` |

```
{"type":"https://httpstatuses.com/403","title":"Forbidden","status":403,
 "detail":"You do not have access to this account.","instance":"/api/accounts/01a015bb-…",
 "errorCode":"ACCESS_DENIED","traceId":"ce10bb069afcbbb8fbf051eef6fe4bd0"}
```

Fifty-three responses understated the body to nothing; five described a response the code cannot
produce. The shared `ProblemDetails` component, meanwhile, declared five members — `type`, `title`,
`status`, `detail`, `instance` — and neither of the two the client branches on.

Three causes, none of them a typo:

- **`errorCode` and `traceId` live in `ProblemDetails.Extensions`**, a dictionary. The component is
  generated by reflecting the type, and reflection cannot see into a dictionary. Fifteen responses
  had already worked around this with hand-written inline schemas, each subtly its own — the
  duplication was the symptom.
- **Two transformers ASSIGNED rather than filled in.** `AuthorizationResponseTransformer` set an
  empty 401/403 "even if already defined", on the stated grounds that "ASP.NET Core JWT Bearer
  middleware returns empty responses without Content-Type". True of the default; this API does not
  use it — `OnChallenge` calls `context.HandleResponse()`, whose entire purpose is to suppress that
  default, and writes JSON. `NotFoundResponseTransformer` carried the same defect with the same
  wrong justification. The assignment also DISCARDED what controllers declared:
  `TransferController` names three step-up codes on its 401 and the line threw them away.
- **`ValidationResponseTransformer` invented 400s on path-only routes.** A `{id:guid}` constraint
  participates in route MATCHING, so a non-GUID matches no route and the framework answers 404
  before model binding exists to fail.

Nothing could catch any of it. The drift gate regenerates the frontend artefacts *from* the document
and compares them, which proves generated code matches the document and never that the document
matches the server. Schemathesis, the one tool that could, ends its step with
`|| true  # report, don't gate`.

## Decision

**The document declares the body, the shared component declares every member the API sends, and a
response nobody can produce is deleted rather than described.**

- **`errorCode` and `traceId` go on the shared `ProblemDetails` component**, via a document
  transformer, because patching one component improves all 89 responses that point at it and a new
  endpoint inherits the truth instead of having to remember it.
- **Both are OPTIONAL, and that is measured rather than cautious.** Seventeen 400s point at this
  component and a model-state failure is one of the shapes they answer: `POST /api/auth/register`
  with a malformed body returns `{type, title, status, errors, traceId}` and no `errorCode`.
  Requiring it would publish a contract wider than the code — the same defect, pointed the other
  way.
- **Transformers fill in, never override.** Where an endpoint declares a status itself, its
  declaration stands. Only the description is completed, and only when it is the bare HTTP reason
  phrase, which is what ApiExplorer writes when nobody wrote anything.
- **A response the endpoint cannot produce is removed.** The four 400s are gone with the branch that
  invented them; the handle lookup's 404 is gone because ADR-0014's enumeration-neutral oracle
  answers 200 with `exists: false`, and the endpoint says so now with `[AlwaysFound]`.

### Why not two components

The plan for this work recommended splitting `ProblemDetails` from a `ValidationProblemDetails`, on
the reasoning that they are genuinely two shapes and an optional-everything object describes
nothing. Phase 1 measured the thing that decides it: **both shapes arrive at the same declared
response**. Seventeen 400s say `typeof(ProblemDetails)` and can answer either. Splitting would have
turned those into a `oneOf` across seventeen call sites and a broad change to generated frontend
types, to express what one optional member expresses exactly. The validation shape already has its
own inline schema where it genuinely stands alone, which is the separation the recommendation was
after.

## Consequences

- **53 responses gained a body and 5 declarations were deleted**; 137 declared responses became 132,
  and the count of refusals declaring no body at all went from 58 to **0**.
- **Twenty-six responses now carry the endpoint's own body instead of the transformer's prose.**
  That is the point of filling in rather than overriding, and it is why the descriptions on those
  are completed from the reason phrase rather than left as `"Forbidden"`.
- **A generated client can now branch on `errorCode`**: `apiSchemas.ts`'s `ProblemDetails` carries
  both members, where before it declared five and the field every error path reads was not among
  them. The hand-written `ProblemDetailsBody` in `problemBaseQuery.ts` STAYS and is not redundant —
  it also models `retryAfterSeconds` and `requiredAuthLevel`, which the BFF adds and the API's
  document therefore cannot describe. What changes is that it is no longer the only place the field
  exists.
- **Two guards, because the pipeline had none.** `PublishedErrorContractTests` reads the committed
  document and refuses an empty refusal body, a missing `errorCode` member, and a *required* one;
  `errorContract.contract.test.ts` asserts the same facts against the answering stack, on both
  targets, so a mock that stops sending `errorCode` fails the build. Both were watched to fail on a
  deliberately broken document before being trusted.
- **What is still not gated:** that the committed document matches a *running* API. That is
  `node scripts/openapi-spec.mjs check`, which no job runs. The guards above close the gap that
  mattered — a document contradicting the code — but a stale commit of it would still pass.
