# Brand assets

Everything visual in this project comes from one file: `frontend/public/logo.svg`. Every icon, at
every size, is generated from it. If the mark ever changes, that file changes and one command
rebuilds the rest.

## The mark

An "A" monogram with an upward arrow sweeping through it and a wave at the lower left, in two flat
colours — **`#0c6ea1`** dark blue and **`#39b8db`** cyan.

Those are the mark's own hexes, measured from the artwork rather than chosen — the modal colours of
the interior regions, where the cyan is bit-identical to `#39b8db` and the dark blue one level from
`#0c6ea1`.

They are _not_ the UI brand colour `#0077b6`, which is the interface accent, but they are the reason
it was picked. Measured: the mark's dark blue sits at hue **200.5°** and `#0077b6` at **200.8°** —
0.3° apart, the same hue at a different saturation. The cyan is at 193.0°. The alternative that was
rejected, `#006DE2`, is at 211.1°, and 10° off reads as subtly wrong precisely where the two meet:
header, sidebar, auth panel.

**The mark was generated by an image model from a text description, and it is not reproducible.**
The same prompt yields a different logo; diffusion is not deterministic. So the raster it came from
was the only instance that existed, which is what made vectorising it worth the effort — a vector
is an asset, a lucky PNG in a downloads folder is not.

That origin also decides how the vectorisation was allowed to behave. There is no original vector
and no designer intent beneath the raster, so every almost-straight edge and every not-quite-symmetric
pair is sampling noise rather than a choice. The vector therefore **regularises**: long edges are
exact lines, corners are the exact intersections of the lines that meet there, the arrow's shaft has
constant width, and the A is symmetric about one fitted axis. What was deliberately _not_ touched is
the composition — proportions, the arrow's gesture, the balance — because that is what makes it this
mark and not another one.

Two artefacts of the generative source survive and cannot be fixed by any amount of tracing: the
source raster's edges rise over about 6 pixels rather than 1–2, and the mark carries a slight
asymmetry in the arrowhead that is far outside noise and was preserved as character.

## Regenerating the icons

```bash
cd frontend
npm install --no-save @resvg/resvg-js   # deliberately not a dependency
npm run generate:icons
```

That writes `favicon.svg`, `favicon.ico`, `favicon-96x96.png`, `apple-touch-icon.png` and both
`web-app-manifest-*.png` into `frontend/public/`. Only `logo.svg` is hand-maintained.

`@resvg/resvg-js` is a native module and the icons change roughly never, so carrying it as a
permanent devDependency would tax every CI install for a script nobody runs. `--no-save` keeps it out of
`package.json`, and leaves the lockfile untouched too, so the install needs no cleanup afterwards.
The script exits with that exact command if the module is missing.

Do not reach for `--no-package-lock` as well: with that flag npm installs **nothing at all** — the
package directory comes out empty and the import fails, which reads like a broken package rather
than a wrong flag.

## Why the generator exists rather than a favicon website

**Each size is rasterised from the vector at its own resolution, never downscaled from one large
PNG.** At 512 the two approaches are indistinguishable, which is exactly why the shortcut survives
unnoticed; at 16 the difference is a legible mark versus a smudge, because the rasteriser needs the
geometry in hand to decide where the antialiasing goes.

Three decisions are baked in that a generic generator gets wrong:

**Coverage differs by role, on purpose.** Maskable icons are cropped by Android to a circle of
radius 40%, so the mark stays at 60% of the width — and the script _asserts_ the bounding box's
half-diagonal fits that circle, because a wide mark can pass a width check and still lose its
corners. The apple-touch icon is opaque and padded, because iOS composites on black and a
transparent icon acquires a dark halo. A plain favicon is never cropped and runs to 94%, since at
16px every pixel of mark is worth having.

**The ICO carries three natively-rendered frames.** Building one by handing a writer a single image
and a list of sizes downscales it — the very thing the script exists to avoid. Worse, some writers
silently drop sizes larger than the base image, so an ICO built from the 16px frame comes out
containing only 16px _and saves without error_. A failure that looks exactly like success.

**16px is a real limit, not a rendering problem.** At that size the arrow is one pixel wide and
cannot read, and the wave at the lower left turns into a smudge across the letter. Dropping the
wave measurably helps; dropping the arrow does not, because without it the A's legs detach from its
apex and the mark falls into three fragments. If a dedicated small-size variant is ever wanted, that
is the direction — not a redraw of the whole thing.

## The originals

The source raster and the earlier hand-made icon set live in the originals archive described in
[ADR-0025](adr/0025-originals-reference-mine.md). Two things in there are traps worth naming:

- The old `favicon.svg` was **760 KB** and contained two base64-embedded PNGs. Not a light and a
  dark variant, as its media query suggests — the two are byte-identical. The same image, twice.
- The generative source ships a _painted_ transparency checkerboard: the grey-and-white pattern is
  in the RGB channels while the alpha channel is fully opaque. Anything that traces or keys that
  file will faithfully reproduce the checkerboard. The usable raster with real alpha is the one
  embedded in the old SVG.
